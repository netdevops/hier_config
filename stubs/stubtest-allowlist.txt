# stubtest allowlist for the `hier_config` package.
#
# `python scripts/build.py stubtest` runs mypy.stubtest against both
# `_hier_config_rust` and `hier_config`, comparing the .pyi stubs against the
# real runtime objects. The extension module is clean and has no allowlist.
#
# Every entry below was audited and falls into one of these categories:
#
#   * pydantic models - `__init__` is synthesised at runtime with a
#     `self` parameter, while the stub uses pydantic's `__pydantic_self__`.
#   * PyO3 enums (`Platform`, `NegationStrategy`, `InterfaceDot1qMode`,
#     `InterfaceDuplex`, `NACHostMode`) - `__new__` takes `value`, and members
#     are native objects rather than the stub's Python enum members.
#   * PyO3 classes - construction happens in `tp_new`, so the runtime has
#     `__new__` where the stub documents `__init__`; the non-`object` C layout
#     also needs `@disjoint_base`, which cannot be expressed for these.
#   * Sentinel defaults - the Rust signatures default to `None` and substitute
#     the real default internally (`style=None` -> `"without_comments"`,
#     `include_tags=None` -> `()`). The stubs document the *effective* default,
#     which is what callers need, so the stub is deliberately more precise.
#   * Stub-only `TypeAlias`es (`SetLikeOfStr`, `JsonValue`, `TextStyle`,
#     `RemediationTransform`) - annotation-only, never materialised at runtime.
#   * Dunder methods that PyO3 exposes as accepting positional-only arguments.
#   * `__all__` - the stubs deliberately omit it; re-exports are explicit.
#
# Unused entries are an error, so this list stays honest: when a divergence is
# fixed the entry must be deleted. Do not add an entry to silence a genuine
# signature mismatch - fix the Rust binding or the stub instead.
